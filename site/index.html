01 / The question

Can transaction patterns reveal risk before a balance event?

The project simulates the analytics infrastructure of a fintech business tracking customer financial health across two institution profiles.

The central hypothesis: customers with concentrated spending and repeated negative monthly cash flow may have both inflexible spending patterns and deteriorating financial buffers.

The analytical output is a risk-signals mart that brings these behavioural indicators together. The platform demonstrates how source data can be ingested, modelled, tested and delivered for downstream decision-making.

Customer financial healthMerchant concentrationCash-flow trendsRisk signals

Designed with data honesty

Plaid Sandbox data is synthetic and does not support real-world predictive conclusions. The project focuses on the correctness of the engineering pipeline and the logic of the analytical models, not on claiming validated customer-risk predictions.

04 / Engineering details

The important work is in the decisions.

The platform documents practical engineering choices made to preserve data integrity, keep the model graph understandable and make orchestration reliable.

01 - INGESTION

Cursor-based synchronisation

Transactions use Plaid's cursor-based sync approach. The cursor advances only after a successful GCS write, so a failed write can be retried from the last known good position.

02 - DATA MODELLING

A complete monthly spine

A generated account-month spine preserves months with zero transactions. This matters when calculating consecutive negative cash-flow periods without treating missing activity as a missing month.

03 - QUALITY

Staging as the control point

Type casting, null handling, field naming and source filters are handled in staging so downstream models inherit consistent, trusted inputs.

04 - ORCHESTRATION

Quality gates in Airflow

Staging tests run before intermediate models. If the quality gate fails, downstream transformation tasks do not proceed on untrusted data.

05 / Learning through debugging

Three subtle bugs. Three important lessons.

Some of the most valuable work came from investigating results that looked plausible but were incomplete or incorrect.

DATA LOADING

Partition overwrites

Sequential WRITE_TRUNCATE operations were replacing previously loaded institution data. The loading order was redesigned so each partition write contained all relevant institutions.

SQL NULL HANDLING

Silent row loss

A pending-transaction filter excluded records where the source returned NULL. Explicit COALESCE handling preserved non-pending rows.

BIGQUERY NAME RESOLUTION

Ambiguous identifiers

A CTE and a column shared a name, leading BigQuery to resolve an ORDER BY reference unexpectedly. Clear naming removed the ambiguity.

The project README documents the investigations, fixes and wider design decisions in more detail.

06 / Scope & limitations

A complete pipeline, with clear boundaries.

The project deliberately prioritised a tested engineering foundation over adding a superficial dashboard layer.

What this project does, and does not, claim.

The dataset is synthetic Plaid Sandbox data, so the resulting risk signals are not validated predictions about real customers. The platform demonstrates a working ingestion-to-mart workflow and the engineering patterns behind it. A live dashboard, production-grade access controls and centralised cursor persistence are documented as future or out-of-scope work.
